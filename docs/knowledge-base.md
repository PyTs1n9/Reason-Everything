# 知识库设计（v1）

> 触发的问题：单篇精读撑不起写论文。文科研究生写一篇综述，参考池动辄 200–500 篇。  
> 核心结论：**知识库不是第七站，而是一层服务 + 一个入口站。** 因为"入库"和"精读"是两种成本量级的事，混在一起必然崩。

---

## 0. 先算一笔账，说明为什么不能"全库精读"

| 做法       | 500 篇的成本                                           | 可行性                  |
| -------- | -------------------------------------------------- | -------------------- |
| 全部跑六站    | 500 × 4 次模型调用 = 2000 次；按 20 万 token/篇算，约 1 亿 token | 不可行，且 95% 的论文你根本不会引用 |
| 全部只做索引   | 0 次模型调用，纯 CPU 约 1 小时                               | 可行                   |
| **三级分层** | **约 40 次调用**                                       | **可行且够用**            |

所以知识库的第一设计原则是：**分级入库，按需加深。**

---

## 1. 三级入库

| 级别        | 每篇成本             | 产出                          | 触发时机         | 能否作为引用依据        |
| --------- | ---------------- | --------------------------- | ------------ | --------------- |
| **L0 索引** | 0 次模型调用（约 7 秒/篇） | 页文本、切块、向量、元数据、页码索引          | 批量拖入时全量执行    | 否，只能"找到"，不能"引用" |
| **L1 速览** | 1 次调用            | 一句话主张 + 5 条要点 + 关键数字（全部带锚点） | 检索命中后，对候选集执行 | 否，可判断"要不要精读"    |
| **L2 精读** | 六站全跑（约 4 次调用）    | 论据卡（支持/反证/条件）+ 审计结论         | 用户勾选"我要引用这篇" | **是，唯一可引用的级别**  |

这条分级的直接效果：**500 篇进来，只有你真正要引的那 5 篇会花掉模型钱。**

---

## 2. 切块：分学科，文科不套 IMRD

理工科论文有 IMRD 结构，文科没有。硬套会把"讨论"切碎，把论证脉络切断。

| 学科   | 切块策略                                                   | 保留字段              |
| ---- | ------------------------------------------------------ | ----------------- |
| 理工   | 按 `Introduction / Methods / Results / Discussion` 感知切分 | 章节名、页码            |
| 人文社科 | 按小节标题（一、二、三 / I. II.）→ 段落组（600–1200 字）→ 10% 重叠         | 小节标题、段落序号、页码、脚注标记 |
| 兜底   | 固定窗口 + 页边界，绝不跨页                                        | 页码                |

三条硬规则：

1. **chunk 不跨页**——否则锚点无法回指。
2. **每个 chunk 必须带 `page` 与 `section`**，缺一个就不入库。
3. **脚注单独成块**（`kind=note`）：文科的溯源大量藏在脚注里，混进正文会被切碎。

---

## 3. 检索：粗排 + 精排 + 过滤

文科检索有一个特殊性：**同一术语在不同学派里意思相反**（"国家能力"在比较政治与公共管理里不是一回事）。纯向量检索会把它们混为一谈。

| 阶段 | 手段                             | 为什么                                   |
| -- | ------------------------------ | ------------------------------------- |
| 粗排 | SQLite **FTS5** 全文检索，取 top 200 | 术语精确匹配，零依赖（已验证本机 SQLite 3.53 支持 FTS5） |
| 精排 | 向量余弦，仅对 200 条重排                | 200×512 维纯 Python 约 20ms，不需要向量数据库     |
| 过滤 | 元数据：年代、学科、文献类型、语言              | 文科常要"近十年、中文、期刊论文"                     |
| 融合 | RRF（倒数排名融合）                    | 两路结果尺度不同，不能直接加权                       |

**不引入向量数据库的理由**：5 万 chunk × 512 维 = 100MB，全量暴力检索也就百毫秒级；FAISS/Milvus 属于过早优化。

---

## 4. 检索结果必须锚点化（这是与前面协议的一致性所在）

检索命中的是一段 chunk，不是一个"相关段落"的感觉。所以每次命中都要走一遍 S1 的定位：

```
chunk → 在页文本中定位 → 生成 Anchor（page + quote + char_span）→ verified
```

- 定位成功 → `anchor verified`，可以进入论据卡、可以进写作
- 定位失败 → 标 `unanchored`，**只能展示，不能被引用**

这一条把知识库和六站接上了：**知识库不生产"看起来相关"，只生产"可回查的片段"。**

---

## 5. 论据矩阵：从"多篇"到"能写"

多篇文献真正的产出不是"摘要合集"，而是一张三栏表：

| 主张         | 支持（谁说的、什么条件）                     | 反证 / 限定（谁反对、边界在哪）                    |
| ---------- | -------------------------------- | ------------------------------------ |
| 睡眠限制损害记忆巩固 | Smith 2024：n=128，20–34 岁，实验室 3 晚 | 高压力亚组无收益（同文 P5）；Jones 2023 在老年样本中未复现 |

矩阵的每一格都是 `ClaimCard`，只是多了 `paper_id` 维度。它不是新数据结构，是已有卡片的**归并视图**——这是"不重复建设"的关键。

**S5 对账在知识库模式下只加一条规则**：跨篇冲突检测（同一主张出现相反结论时，必须并列展示，不得只留一方）。

---

## 6. 引注：机械生成，不交给模型

文科的刚需是脚注与参考文献格式（GB/T 7714、Chicago、MLA）。这是纯粹的字符串拼装：

```
Paper 元数据（作者/题名/期刊/年/卷期/页码/DOI） + Anchor.page → 引注字符串
```

- 元数据缺失 → 输出 `[元数据不全]` 占位，不猜
- 同一文献多次引用 → 自动生成"同上"或短格式
- 格式模板放 `templates/citation/*.json`，与渲染器解耦

---

## 7. 单机可行性（实测口径）

| 项                      | 估算                  |
| ---------------------- | ------------------- |
| 500 篇 × 20 页           | 10,000 页            |
| chunk 数（5/页）           | 约 50,000            |
| 向量存储（512 维 float32）    | 约 100MB             |
| SQLite 库（文本 + 向量 + 索引） | 约 300–400MB         |
| 全量 L0 入库耗时             | 约 1 小时（可断点续跑）       |
| 单次检索延迟                 | FTS5 ≤20ms，精排 ≤50ms |

**结论：不需要服务端，不需要向量数据库。** 一台普通笔记本足够撑 500 篇。

## 8. 与六站的接口变化

| 站             | 变化                              | 说明                |
| ------------- | ------------------------------- | ----------------- |
| **S0 检索（新增）** | 输入"我要论证什么" → 输出候选论文 + 命中片段（带锚点） | 只在知识库模式下出现；单篇模式跳过 |
| S1 拆解         | 支持批量与增量；写入 chunk 与向量            | 幂等：同 hash 不重复解析   |
| S2 取证         | 增加 `paper_id` 入参                | 支持跨篇取证            |
| S3 质疑         | 增加"跨篇对立观点"抽取                    | 文科的核心证据形态         |
| S4 划界         | 不变                              | 条件仍来自单篇原文         |
| S5 对账         | 增加跨篇冲突规则                        | 见 §5              |
| S6 编译         | 增加论据矩阵页、引注表                     | 产物从"单篇包"变成"综述包"   |

数据流：

```
批量 PDF ─→ L0 索引（全量，0 调用）
                ↓
        用户：我要论证 X
                ↓
        S0 检索 → 候选 20 篇 → L1 速览（20 次调用）
                ↓
        用户勾选 5 篇 → L2 精读六站（20 次调用）
                ↓
        S5 对账（含跨篇冲突） → S6 编译 → 综述包（含论据矩阵 + 引注）
```



---

## 9. 文科适配：换判据，不换架构

六站不变，但 S3/S4 的判据要换一套。这是"架构稳定、判据可插拔"的直接体现。

| 站     | 理工判据          | 文科判据                                    |
| ----- | ------------- | --------------------------------------- |
| S3 质疑 | 样本量、方法局限、统计效力 | 材料覆盖范围（只研究了哪段时期/哪个地区）、对立学派的批评、作者承认的解释竞争 |
| S4 划界 | 人群、任务、模型、数据集  | 时期、地域、文本类型、理论传统、分析单位                    |
| 证据形态  | 数据与指标         | 文本、档案、案例、谱系                             |

**不要为文科另建一套流水线。** 换判据表（`criteria/humanities.json`）即可，节点与协议不动。

## 10. 实施切分（不改现有 5 天计划）

| 期             | 范围                                                                                          | 说明          |
| ------------- | ------------------------------------------------------------------------------------------- | ----------- |
| **当前 5 天**    | 只做**预留**：`chunk` 表带 `page/section/anchor_id`；`Paper` 加 `source_type` 与 `batch_id`；S1 支持批量入参 | 不引入检索，不阻塞主线 |
| **P1（第 2 周）** | L0 全量索引 + FTS5 检索 + 锚点化命中                                                                   | 先能用"搜得到"    |
| **P2（第 3 周）** | L1 速览 + 论据矩阵 + 引注                                                                           | 能支撑写作       |
| **P3**        | 引文网络（参考文献列表 → 边）、跨篇冲突                                                                       | 综述的深水区      |

先做 L0 是刻意的：**没有索引的知识库只是文件夹**，而索引本身不需要模型，最便宜、最快见效。

---

## 11. 不做什么

| 不做         | 原因                          |
| ---------- | --------------------------- |
| 自动写综述      | 多篇 + 生成 = 幻觉放大器；只出矩阵与骨架，人来写 |
| 全文向量化后直接问答 | 没有锚点的问答无法核验，等于换个地方编         |
| 服务端多租户     | 本地单机已够 500 篇；上线再谈           |
| PDF 内高亮    | 已决策不做，检索命中也只到"页 + 摘句"       |
| 引文网络自动补全   | 参考文献列表格式混乱，先做"能匹配上的"，不做"猜"  |
