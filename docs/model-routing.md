# 模型路由设计

> 起因：上一版只有一个 `MODEL_API_KEY`，等于把整个工作流交给一个模型。  
> 这不是 agent 工作流，是把 LLM 当成一个函数调用。
>
> 一句话结论：**工作流里的每个岗位声明"角色"，由路由决定用哪个模型、失败降级给谁、花多少钱。**



---

## 1. 为什么必须异构

| 岗位       | 需求            | 用错模型的后果               |
| -------- | ------------- | --------------------- |
| 取证       | 便宜、快、温度低、长输入  | 用最贵的模型抽卡，一篇 20 页烧掉几美元 |
| 笔记起草     | 强推理、能组织长文     | 用便宜模型写，结构散、条件丢        |
| **内容评审** | **必须与生成不同模型** | 同一模型自评，会放过自己刚犯的同类错误   |
| 划界       | 温度 0、只做抽取     | 温度高会"补充"原文没有的条件       |
| 嵌入（知识库）  | 本地小模型、批量      | 用对话模型做嵌入，成本高一个量级      |

**最重要的一条不是省钱，是第三条**：同一模型既写又评，评审会因为相同的偏好放过相同的错误。异构是门禁有效性的前提，不是优化项。

---

## 2. 角色矩阵

| 角色          | 对应站     | 模型档位      | 温度  | 单次上限 | 失败降级       |
| ----------- | ------- | --------- | --- | ---- | ---------- |
| `evidence`  | S2 取证   | 便宜 / 长上下文 | 0.1 | 4k   | → `strong` |
| `challenge` | S3 质疑   | 强推理       | 0.5 | 4k   | → `strong` |
| `scope`     | S4 划界   | 便宜        | 0.0 | 2k   | → `strong` |
| `note`      | 笔记/综述起草 | 强         | 0.3 | 8k   | 无（失败即停）    |
| `audit`     | S5 内容评审 | **另一家模型** | 0.0 | 6k   | → `strong` |

降级链的顺序必须与成本递增一致：**先便宜后贵**，否则降级没有意义。

---

## 3. 三种路由，只用最简单的那种

| 方式                  | 用不用    | 理由                |
| ------------------- | ------ | ----------------- |
| 静态映射（角色 → 候选链）      | **用**  | 可预测、可测试、可解释       |
| 按输入规模选档（页数 / 字符数阈值） | **用**  | 规则确定，日志可复核        |
| 让 LLM 决定用哪个模型       | **不用** | 多一次调用、不可复现、出错无法归因 |

> 反直觉但重要：**元路由（meta-router）是伪需求。** 判断"哪篇论文该用大模型"本身就需要大模型，成本抵消收益，还把可复现性弄丢了。

---

## 4. 预算护栏

```toml
budget_usd = 2.0
```

- 每次调用前检查 `已花 ≥ 上限`，超了直接抛 `BudgetExceeded`，**不静默降级成便宜模型**（降级会让人以为结果质量没变）。
- 单次调用无法预知成本，所以第一次总是允许；护栏保证的是"不会持续烧"。
- 超预算的运行状态标 `partial`，已产出的卡片保留，manifest 写明停在哪一站。

---

## 5. 可观测：每次调用都留痕

trace 每条记录包含：

```json
{"node": "cards", "model": "small-model", "profile": "cheap",
 "tokens_in": 18240, "tokens_out": 1520, "cost_usd": 0.0036, "elapsed_ms": 4210}
```

运行级汇总写进日志与 manifest：

```json
{"calls": 6, "tokens_in": 96400, "tokens_out": 8120, "cost_usd": 0.0521,
 "by_role": {"evidence": {"calls": 1, "model": "small-model", "cost_usd": 0.0036}}}
```

这让三件事变得可回答：

1. 这份包是用哪个模型生成的？
2. 哪一站最贵？
3. 评审用的模型和写作的是不是同一个？（如果不是，才叫异构评审）

## 6. 配置

复制 `models.example.toml` 为 `models.local.toml`：

```toml
budget_usd = 2.0

[profiles.cheap]
base_url = "https://api.example.com/v1"
model = "small-model"
api_key_env = "MODEL_API_KEY"
temperature = 0.1
cost_in = 0.15
cost_out = 0.60

[profiles.judge]
base_url = "https://api.other-vendor.com/v1"
model = "another-model"
api_key_env = "JUDGE_API_KEY"
temperature = 0.0

[routing]
evidence = ["cheap", "strong"]
audit    = ["judge", "strong"]
```

- 密钥用 `api_key_env` 指向环境变量，配置文件可以进版本库
- `cost_in / cost_out` 是每百万 token 单价，用于算成本；不填则只记 token
- 旧版 `config.local.toml` 与环境变量仍然兼容，会被折算成"单 profile、所有角色指向它"

## 7. 与"单链"的区别

| 维度    | 单链（旧）            | 路由（新）                                     |
| ----- | ---------------- | ----------------------------------------- |
| 模型数量  | 1                | N，按岗位分配                                   |
| 评审独立性 | 自己评自己            | 强制换模型                                     |
| 失败处理  | 整条链失败            | 降级到备用模型，trace 标 `fallback`                |
| 成本    | 不可见              | 每次调用记账，可归因到站                              |
| 换模型   | 改代码 + 重启         | 改一行 TOML                                  |
| 可复现   | "用的是那个模型"（说不清版本） | manifest 记录 profile / model / prompt_hash |



---

## 8. 不做什么

| 不做       | 原因                           |
| -------- | ---------------------------- |
| 自动比价选模型  | 需要先跑一遍才知道效果，等于双倍成本           |
| 让模型自己选模型 | 不可复现，且多一次调用                  |
| 为省钱牺牲评审  | 评审是这条链唯一的否决权，不降级             |
| 隐藏降级     | 降级必须在 trace 与 manifest 里显式标注 |

## 9. 总 Agent 到底管什么（与路由的边界）

「总 Agent」不是一个 LLM，而是**三个不同频率的决策层**。把它们混成一个"大脑"，是上一版最大的表述问题。

| 层 | 由谁做 | 决策频率 | 决策内容 | 例子 |
| --- | --- | --- | --- | --- |
| **规划** Planner | LLM | 每次运行**一次** | 这次跑哪些站、并行还是串行、预算档位、要不要查知识库 | "这篇 6 页的方法论文" → 快速体检（跳过高成本站） |
| **编排** Orchestrator | 代码 | 全程，每站 | 顺序、重试、降级、checkpoint、并发度 | S4 超时 → 标 `partial` 继续，不拖垮整条链 |
| **配置** Router | TOML | 每次调用前 | 角色 → 模型链 | `evidence → cheap → strong` |

三者的区别是**决策频率**与**可复现性要求**：规划一天变一次，编排每秒在变，配置一个月变一次。

### 为什么"选模型"不该进 Planner

1. 它是**资源配置**，输入是价格与配额，不是语义。用语义模型解资源配置题，是拿错工具。
2. 每调一次模型就再问一次"用哪个模型"，**净增一次调用**，成本抵消收益。
3. 不可复现：同样的论文两次跑，可能选中不同模型，出问题无法归因。
4. 学术界的 learned router（如 RouteLLM）是**离线训练出来的分类器**，不是运行时去问大模型。

唯一例外：模型池 > 20 个且能力差异细微到人无法手写映射时，才值得训一个小分类器。你现在是 3–5 个模型，手写映射更准、更便宜、可审计。

### 什么才算"全自动"

> 全自动 = 人只给输入与目标，中间不需要点确认、不需要填参数、不需要看日志才知道下一步。

规则引擎和配置文件**不破坏**自动化，它们是"事先写好的决策"。反过来说：如果每一步都要问模型，全自动在经济上不成立——一条链 6 次调用变成 12 次，延迟翻倍。

**全自动 ≠ 全模型判断。**

### Supervisor：大脑真正该出场的地方

正常路径上，Planner 说完一次就闭嘴。真正需要第二次"思考"的是异常：

| 触发条件 | Supervisor 动作 | 上限 |
| --- | --- | --- |
| 连续 2 站失败 | 重规划：换模型档位 / 砍掉低价值站 | 1 次 |
| 评审冲突且无法按 `target_stage` 路由 | 重规划：换评审模型复判 | 1 次 |
| 预算剩余 < 20% | 降档：跳过高成本站，保底出包 | 1 次 |
| 正常路径 | **不调用** | 0 次 |

一句话：**大脑负责"这次怎么跑"，不负责"这次用哪个模型"。**
